# 全局执行规则

本规则适用于本包所有 P0、P1、P2 任务。单项任务可增加更严格约束，但不得降低本规则要求。

## 1. 开始前的调查与范围控制

1. 先发现并完整阅读项目级和目录级指令（如 `AGENTS.md`）、相关设计、最新代码、测试、配置、调用链及 `git status`；修改前再次读取将要编辑的文件。
2. 保持变更范围干净：列出允许修改的文件，检查工作区既有变更；不覆盖、回退、暂存或提交无关变更。
3. 必须先调查、再设计、再实施。HTML 优化报告中的候选文件、行号和结论仅是待重新核验的证据，不能视为当前事实；均须在当前代码中重新验证，禁止盲改。
4. 功能新增和缺陷修复使用测试先行的红—绿—重构流程，并补充覆盖真实行为的测试；不得以 mock 替代必要的集成或端到端验收。
5. 删除文件、模块、数据、容器或数据库前，必须全局检查引用、列出影响范围并取得用户明确授权；未授权时不得删除或移动。

## 2. 跨层一致性与安全

1. 每次跨模块修改均检查数据结构、ORM/模型、Schema/迁移、API DTO、前端类型和展示、路由/网关、Docker、环境变量及多数据库连接是否同步；不得让 A 库 API 误连 B 库。
2. 面向用户的失败信息必须是清晰的纯文本；不得暴露 JSON/对象字符串、异常堆栈、SQL、密钥、令牌或内部实现。全局异常处理对象错误应提取 `message` 字段，而非直接字符串化。
3. 密钥、密码、令牌、连接串和真实用户数据不得硬编码、打印、提交或写入截图；日志与报告须脱敏。
4. AI 相关任务必须保留“出题 Agent + 审题 Agent”两层约束；不得恢复 `prompts_2` 的复杂多层出题架构。

## 3. 数据库、容器与运行安全

1. 数据库任务在执行任何 backup、migration、restore 或 rollback 前，必须核验并记录目标 `host`、`database` 和 `environment`，确认其与预期一致后才可继续，防止在错误目标执行破坏性操作。先完成备份；在独立、可丢弃的测试数据库验证迁移或恢复，提供 upgrade、downgrade（如适用）或隔离恢复路径和回滚证据。不得在唯一数据副本上试验。
2. 涉及事务或并发时，验证幂等、重复请求、并发写入和部分失败回滚。
3. 修改应用代码后，容器化项目必须重新构建镜像并启动更新（例如 `docker compose up -d --build`）；仅文档修改时不得无意义重建。修改编排文件或环境变量后重新执行 `up -d`，并检查 `docker ps` 与 Docker Desktop 是否报错。
4. 关键创建、写入、调用和服务操作必须有足够的结构化日志上下文；验收中检查日志、健康状态及是否引入新增错误。

## 4. UI 与回归验收

1. UI 任务必须通过内部浏览器完成真实操作；检查控制台、响应式视口和目标响应，并保存截图作为验收证据。不得仅凭代码审查或 mock 宣称 UI 已验收。
2. 前端任务同时覆盖 loading、empty、error、offline、重试、键盘操作和移动端视口。
3. 完成前执行与风险匹配的单元、集成、端到端测试、构建、日志和健康检查；失败时先定位、修复并重新验证。
4. 提交前运行 `git diff --check`，审计 `git diff`、`git status` 和暂存范围，确保只包含该任务允许的变更。

## 5. 固定最终证据报告

每项任务的最终报告必须按以下顺序提供：

1. 任务状态与目标；
2. 实际修改的文件及关键设计决策；
3. 调查结论与重新验证的假设；
4. 测试、构建、健康检查、日志和 Git 范围审计的命令及结果；
5. 数据库备份、隔离恢复/迁移和回滚证据（如适用）；
6. 内部浏览器真实操作、控制台/响应式检查和截图路径（UI 任务必填）；
7. 提交 SHA；
8. 残余风险、已知限制和需要人工执行的步骤。
