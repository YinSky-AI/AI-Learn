# P0-02：后台访问控制（Access Control）

将本文件完整交给编码 AI 执行。先调查、后设计、再实施；HTML 旧行号仅为待核验证据。遵守 `AGENTS.md` 与 `docs/prompts_4/00-global-execution-rules.md`，并保持“出题 Agent + 审题 Agent”两层 AI 约束。

## 任务定位

- 优先级：P0；风险：极高（管理面可被伪造身份写入）。目标是集中管理员身份与授权，使用签名、可过期、可撤销的会话，覆盖 CSRF、防越权和审计。
- 非目标：不在本任务顺带重写全部后台领域，不改普通用户账号主体方案（P1-09），不以静态 Cookie 或共享密码作为任何过渡安全边界。

## 当前证据

- Finding 2 的候选文件为 `backend/app/admin/routes.py:26,94-155,436-1662`、`core/config.py:71`；疑似有默认密码 `admin123` 和可伪造的固定登录 Cookie。
- 影响是攻击者可能获得课程、用户、课时和题目的写权限。建议是集中管理员身份、签名会话、过期/撤销、CSRF、权限与审计；收益是一条真实身份边界覆盖所有后台操作。
- 必须重新核验当前认证配置、Cookie 属性、路由守卫、所有写操作、模板/前端表单、测试及部署变量。

## 开始前调查

1. 读取现有认证、管理员模型/角色、配置加载、密码哈希、路由依赖、中间件、模板、测试与 `git status`。
2. 全局搜索默认凭据、Cookie 写读、后台 URL、状态改变方法、CSRF 豁免、权限判断和审计；区分真实当前问题与报告历史。
3. 明确会话密钥来源、轮换/撤销语义、固定生命周期、Secure/HttpOnly/SameSite 属性、CSRF 方案和最小角色矩阵；任何生产密钥、账号迁移或外部 IdP 接入须先取得用户授权。

## 允许修改范围

- 可修改实现集中管理员认证所需的配置读取、认证/会话服务、路由守卫、CSRF 校验、审计接线、模板/表单、测试及最小部署文档/示例（不得写入真实密钥）。
- 可以新增经过命名的管理员身份/授权模块及测试；须维持已有合法后台工作流或提供受控迁移。
- 不修改 P0-03 的软删除领域策略、无关前端、数据库拓扑或题库访问策略。

## 禁止操作

- 禁止默认管理员密码、固定/未签名 Cookie、客户端自报角色、在 URL/日志/截图暴露凭据，或以关闭 CSRF 来“修复”表单失败。
- 禁止只保护页面 GET 而遗漏 POST/PUT/PATCH/DELETE、导出、批量操作和异步入口；禁止用 mock 替代真实 Cookie/session/CSRF 测试。
- 禁止删除账号、会话或数据库数据；涉及认证数据迁移必须先列出影响范围、备份、验证目标并获得授权。

## 分阶段执行

1. 调查：列出所有后台入口、状态变更和共享资源，确认不与 P0-01/P0-03 并行编辑认证、路由或全局配置。
2. 设计：定义最小可信管理员主体、签名会话、过期/撤销、CSRF、授权矩阵和审计事件；审查兼容与登录迁移方案。
3. 测试先行：为登录、伪造/篡改 Cookie、过期会话、撤销、CSRF 缺失/错误、未授权和越权写入写失败测试。
4. 最小实施：集中校验并接入全部后台写入口，移除已确认的不安全默认行为；任何配置改动均使用环境注入且脱敏。
5. 自主验收：运行认证与路由测试、真实浏览器表单流程、日志/健康检查；应用或配置改动按规则重建/重载容器并检查 `docker ps` 与 Docker Desktop。

## 跨模块耦合检查

- 同步检查管理员模型、会话存储、路由/模板、API/DTO、反向代理 Cookie 转发、环境变量、Docker 和审计持久化。
- 逐个确认所有管理域（课程、用户、课时、题目及批量/导出操作）共用同一授权决策，且 P0-03 可复用身份与审计上下文。
- 检查主库/题库连接与管理员操作目标，防止权限正确却连接到错误数据库；记录对未来前端契约的影响。

## 错误处理要求

- 登录失败、会话过期、CSRF 失败、未认证和未授权必须返回用户可理解的纯文本/安全页面，不能泄露账户是否存在、密钥、堆栈、SQL 或对象内容。
- 记录脱敏的登录、撤销、拒绝和授权审计事件（操作者/请求关联 ID/目标类型），不记录密码、Cookie、令牌或 CSRF 值。
- 出现迁移或发布失败时撤回到已验证会话实现；不保留临时旁路。

## 验收标准

- 真实 HTTP 和浏览器测试覆盖有效登录、签名篡改 Cookie、过期会话、主动撤销、登出后复用、未认证、低权限越权、所有危险写方法和 CSRF 缺失/错误；全部均得到预期拒绝或成功。
- 断言 Cookie 使用适当签名及 `HttpOnly`、`Secure`（按部署环境）和 `SameSite` 属性，且默认/硬编码凭据不在源码、配置输出或日志中。
- 授权成功的管理变更产生可检索的脱敏审计记录；浏览器操作检查控制台、响应式视口和截图证据。
- 测试、构建、日志/健康、Docker 状态、`git diff --check` 与 Git 范围审计通过。

## 最终报告格式

依次给出：状态与目标；修改文件和会话/CSRF/权限设计；Finding 2 复核结论；测试、构建、浏览器、容器、日志、健康和 Git 命令结果；数据库备份/恢复证据（如适用）；截图路径；提交 SHA；残余风险和需人工配置的密钥/轮换步骤。全部敏感值脱敏。
