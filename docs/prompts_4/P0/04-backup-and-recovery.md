# P0-04：备份与恢复（Backup & Recovery）

将本文件完整交给编码 AI 执行。数据库与容器操作均为高风险：先调查和验证目标，再设计、测试先行、最小实施。严格遵守 `AGENTS.md` 与全局规则；保持“出题 Agent + 审题 Agent”两层约束不被削弱。

## 任务定位

- 优先级：P0；风险：极高（不可恢复的数据丢失）。目标是定义可证明的 PostgreSQL 备份与恢复能力：RPO/RTO、加密备份、异地保留、校验和、受控保留策略及定期隔离恢复演练。
- 非目标：不在唯一数据副本上试验，不擅自删除 volume/数据库/备份，不把“本机 named volume”误当备份，也不在本任务改业务 Schema。

## 当前证据

- Finding 4 候选证据为 `docker-compose.yml:23-25,136-140`，且仓库可能不存在 `pg_dump`、`pg_restore`、WAL 或恢复演练。PostgreSQL 疑似只依赖本地 named volume。
- 影响是磁盘、Docker 数据目录或误删除事故可造成不可恢复损失。建议为 RPO/RTO、加密异地副本、校验和和恢复演练；收益是用小型运维接口提供可证实的灾难恢复。
- 必须重新核验当前 compose、存储、连接配置、密钥管理、运行环境、已有备份、网络/权限与合规约束。

## 开始前调查

1. 阅读 compose、数据库配置、运行/部署脚本、Makefile、环境变量来源、现有备份文档、监控和 `git status`；列出允许修改文件。
2. 在执行任何 `pg_dump`、restore、migration 或 rollback 前，显示并记录目标 `host`、`database`、`environment`，并与预期逐项核对；错误或不确定即停止。
3. 明确 RPO/RTO、备份频率、保留、加密密钥托管、异地目标、访问控制、校验、告警与恢复负责人。生产备份目标、凭据、外部存储和保留删除策略必须取得用户明确授权。

## 允许修改范围

- 可修改或新增最小化的备份/校验/恢复演练脚本、受控配置、compose 接线、运行文档、监控告警接线和对应测试；脚本不得嵌入真实连接串或密钥。
- 可创建独立、明确标记为可丢弃的恢复数据库/容器用于演练；其名称和连接目标必须经过二次确认。
- 不修改业务模型/数据、迁移链或无关服务；不删除现有 volume、数据库、对象存储或备份。

## 禁止操作

- 禁止在未验证的 host/database/environment 上执行 dump、restore、清理、覆盖、`DROP`、volume 删除或生产回滚；禁止将恢复导向原库。
- 禁止只测试脚本返回码而不运行真实 `pg_dump` 与真实隔离 `pg_restore`；禁止在仓库、日志、CI 输出或截图泄露密钥/真实数据。
- 禁止不经授权配置外部存储、删除过期备份或改变生产调度。

## 分阶段执行

1. 调查：复核 Finding 4、依赖与实际存储，列出数据资产和故障域；确认本任务不与 P0-05/P0-06/P0-07 并行编辑数据库连接或编排。
2. 设计：经授权制定 RPO/RTO、加密、异地、校验、保留、恢复与告警设计，并输出目标验证和回滚清单。
3. 测试先行：为目标拒绝、校验失败、备份失败、恢复失败及脚本安全保护编写测试；预建隔离恢复环境。
4. 最小实施：实现可审计备份流程，使用真实 `pg_dump` 生成备份，再在独立可丢弃目标运行 `pg_restore`；记录校验和与恢复时间。
5. 自主验收：验证恢复后关键表/行数/约束或业务查询，检查日志、告警、容器健康；应用/编排变动按规则重建或 `up -d` 并检查 `docker ps`、Docker Desktop。

## 跨模块耦合检查

- 核对主库和题库的每个连接串、Session/服务目标、compose volume/网络、环境变量和权限，防止备份或恢复 A 库时误操作 B 库。
- 检查备份对迁移（P0-07）、事务数据（P0-05）、管理员恢复（P0-03）、监控/CI 和部署的接口影响。
- 验证加密/密钥、异地存储、日志与告警不会泄露数据，且 Docker 启动顺序不把恢复任务当业务容器。

## 错误处理要求

- 目标不匹配、凭据缺失、校验失败、空间不足、dump/restore 失败应停止后续破坏性步骤，返回清晰纯文本摘要并记录脱敏上下文、命令阶段与关联 ID。
- 不输出连接串、密码、令牌、完整 SQL 或真实用户行；对象异常只使用 `message`。
- 失败必须保留原库不变、隔离失败目标可安全清理（经确认），并提供明确回滚/人工升级路径。

## 验收标准

- 提供真实 `pg_dump` 产物及校验和证据，并证明备份已按经授权的加密与异地/独立故障域策略保存；报告不得包含敏感值。
- 在独立、可丢弃且已验证的数据库执行真实 `pg_restore`，校验关键 Schema、行数/业务查询、约束和可读性，记录恢复耗时并对照 RPO/RTO。
- 故意模拟校验/目标错误时脚本拒绝执行；原生产/源数据库没有改动。恢复演练日志、告警和容器健康状态无新增错误。
- 相关测试、脚本校验、`docker ps`/Docker Desktop、`git diff --check` 与 Git 范围审计通过；附运行命令、脱敏日志和恢复证据。

## 最终报告格式

按顺序写：状态与目标；修改文件和备份设计；Finding 4 复核；目标 host/database/environment 二次验证；真实 dump、校验、隔离 restore、测试、容器、日志和 Git 命令结果；恢复演练证据；截图路径（若有 UI）；提交 SHA；残余风险、RPO/RTO 假设及需要授权人员配置的外部存储/密钥步骤。
