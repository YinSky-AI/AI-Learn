# P1-09：账号主体（Account Principal）

将本文件完整交给编码 AI 执行。先调查当前代码再设计和实施；HTML 行号只是候选证据。严格遵守 `AGENTS.md` 与 `docs/prompts_4/00-global-execution-rules.md`。

## 任务定位

- 优先级 P1；风险高（撤销和停用未及时生效）。建立统一 Account Principal：每个受保护写操作均基于真实账号状态、凭证版本和撤销时间授权，而非仅信任可解码 JWT `sub`。
- 非目标：不替换全部认证体系、不变更无关业务权限，也不在本任务恢复多 Agent 出题架构。

## 当前证据

- Finding 9 候选为 `backend/app/core/deps.py:29-105`、`core/security.py:103-132`、`api/v1/learning.py`、`api/v1/questions.py`：写入口疑似只验证 `sub`，refresh `jti` 未持久化、轮换消费或撤销。
- 旧 access/refresh token 可在账号删除、停用或泄露后继续使用；建议将 status、credential version、`revoked_at` 集中为主体解析边界，使敏感状态变更立即覆盖业务模块。逐项在当前代码复核。

## 开始前调查

1. 阅读认证模型、JWT/refresh 签发与刷新流程、依赖注入、中间件、所有写路由、管理变更和现有测试；记录 `git status`。
2. 搜索所有直接读取 `sub`、绕过认证依赖、token 黑名单/版本和账户状态的调用，画出 access、refresh、session/cookie 的实际语义。
3. 若停用、删除和多设备登出规则未定义，先提出最小兼容方案并请求确认。

## 允许修改范围

- 可修改账号/凭证模型、认证依赖、安全服务、受保护路由适配、必要迁移及单元/集成/浏览器测试；接口演进须保持兼容或有迁移说明。
- 数据库变化先核验并记录目标 host、database、environment，备份后只在独立可丢弃测试库验证 upgrade/downgrade 或隔离恢复。

## 禁止操作

- 禁止仅在个别路由补判断、信任客户端传来的主体、硬编码密钥/令牌，或删除用户/凭证/历史数据。
- 禁止以 mock 替代真实鉴权响应，禁止吞掉认证异常或将堆栈、SQL、对象字符串返回用户。

## 分阶段执行

1. 调查并列出所有主体消费者及与 P0-02/P0-03 的共享认证边界；2. 设计唯一 Principal 与令牌失效语义；3. 先写失败测试；4. 以最小集中依赖实施并适配调用方；5. 运行真实接口、构建、日志和健康验收。

## 跨模块耦合检查

- 同步检查用户 ORM/Schema/迁移、JWT payload、refresh 存储、API DTO、前端登出/刷新处理、网关与环境配置；确认 A 库 API 不会连至 B 库。
- 检查管理员状态变更、学习和题目写入是否都经同一主体，且不会破坏 P0 的会话、CSRF、审计和授权约束。

## 错误处理要求

- 无效、过期、撤销、版本不匹配和已停用主体均返回清晰、统一的纯文本安全错误；不泄露账号是否存在、令牌内容或内部原因。
- 记录脱敏主体标识、原因类别和关联 ID；对象型异常提取 `message`，失败事务回滚。

## 验收标准

- 集成测试证明：正常主体可访问；access/refresh 过期、撤销、refresh 重放、轮换后旧 refresh、credential version 变更、账号禁用和删除均立即拒绝所有已调查写入口。
- 并发刷新不会产生多个有效后继凭证；状态变更有审计且不泄露敏感值。前端真实登出/失效路径不陷入循环。
- 如 UI 变更，内部浏览器完成真实登录、停用/撤销后的操作流程，检查 console、移动视口与响应，并保存截图；测试、迁移隔离回滚、日志/健康、`git diff --check` 均通过。
