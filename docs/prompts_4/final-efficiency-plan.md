# prompts_4 提效执行方案（最终版）

本方案用于在保证完整交付的前提下减少无效往返，不改变 prompts_4 的功能约束。

## 执行节奏

1. 主 Agent 先读取仓库指令、提示词、代码、测试和 Git 状态，按依赖顺序一次选择一个最小可验收任务。
2. 默认由主 Agent 直接实施；只有存在互不依赖且文件范围不重叠的调查任务时才使用子 Agent。
3. 每项先运行相关测试，再做最小修改，最后运行目标测试和一次必要的回归测试；大规模或高风险改动再增加独立审查。
4. 连续任务集中汇报，按“已完成、验证证据、阻塞项、下一步”汇总，避免每个小错误都打断主流程。

## 验证与环境

- 后端先构建一次镜像，再执行目标测试；所有任务完成后执行完整后端测试、前端测试、类型检查和生产构建。
- 修改应用代码后使用 `docker compose up -d --build --wait`，并检查 `docker compose ps`、健康端点和相关日志。
- 只有 UI/交互发生变化时才使用内部浏览器；保存真实操作截图和控制台证据。无需 UI 验证时不控制电脑。
- 使用原始数据库仅限已授权的迁移/恢复场景，先备份并记录目标、审批引用和迁移头；普通测试使用可丢弃测试库。

## 质量闸门

- 不跳过安全、数据一致性、跨模块契约和回归验证。
- 不为追求速度恢复 prompts_2 的多层出题架构，也不扩大任务范围。
- P2-20 的保留/删除/匿名化策略必须等待业务、法务和隐私书面确认；未确认前保持未完成，不以技术实现替代合规决策。
