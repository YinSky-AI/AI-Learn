# 项目 Agent 指令重构设计

## 1. 背景

仓库根目录当前只有 `agent.md`，没有多数编码 Agent 会自动发现的标准文件 `AGENTS.md`。现有 `agent.md` 仍将项目描述为八层出题、PID 反馈与 SummaryAgent 自进化系统，并引用不存在的 `agents/` 目录和已失效的绝对项目路径。这与当前代码、`docs/prompts_3/` 的两层出题实现及 `docs/prompts_4/` 的执行约束冲突。

本次只重构项目指令与文档入口，不修改业务代码、配置、数据库、Docker 或提示词任务正文。

## 2. 方案比较

### 方案 A：只改现有 `agent.md`

优点是文件改动最少。缺点是文件名不是标准 `AGENTS.md`，其他会话和工具可能不会自动加载，`prompts_4` 中对 `AGENTS.md` 的引用仍然失效。

### 方案 B：新增 `AGENTS.md`，保留旧 `agent.md` 全文

优点是兼容标准发现机制。缺点是两个入口会并存完整规则，旧八层架构仍可能被误读，后续容易出现重复和漂移。

### 方案 C：标准 `AGENTS.md` + 精简兼容入口（采用）

新增根目录 `AGENTS.md` 作为唯一执行规则；将 `agent.md` 缩减为兼容导航，只链接 `AGENTS.md` 与 `docs/INDEX.md`；同步更新 `docs/INDEX.md`。该方案同时解决自动发现、旧架构冲突和入口重复问题。

## 3. 文件职责

### `AGENTS.md`

作为仓库唯一权威的 Agent 执行规则，包含：

1. 项目现状和文档权威顺序。
2. 当前架构摘要：FastAPI、Next.js、PostgreSQL、Redis、两层 AI 出题和四角色辅导。
3. 标准流程：调查 → 计划 → 实施 → 自主验收 → 结果报告。
4. 文件、删除、密钥、数据库、错误处理和跨模块耦合安全规则。
5. 按变更类型区分的验收矩阵。
6. `prompts_4` 一次只执行一个任务的协议。
7. Git 分支、Conventional Commits、受保护 `main`、PR 和 Squash merge 规则。
8. 明确禁止恢复 `prompts_2` 的复杂出题架构。

该文件不写本机绝对路径，项目根目录始终表示当前 Git 仓库根目录。

### `agent.md`

保留文件以兼容现有链接，但内容缩减为入口说明：

- 执行规则读取 `AGENTS.md`。
- 文档导航读取 `docs/INDEX.md`。
- 当前设计以 `docs/prompts_3/` 为依据。
- `docs/prompts_4/` 是尚未实施的优化待办。
- `docs/prompts_2/` 只作历史参考。

### `docs/INDEX.md`

把 `AGENTS.md` 标为标准执行入口，把 `agent.md` 标为兼容入口，并保持 `prompts_3` 与 `prompts_4` 的状态区别。

## 4. 权威顺序

发生冲突时按以下顺序判断：

1. 当前代码、数据库模型、迁移和可执行测试是实现事实。
2. 根目录 `AGENTS.md` 是执行与安全规则。
3. `docs/prompts_3/` 是当前已实施功能的设计依据。
4. `docs/prompts_4/` 是尚未实施的优化待办，不代表当前状态。
5. `docs/prompts_1/` 是早期产品背景。
6. `docs/prompts_2/` 是历史题库方案，不得恢复其复杂多层出题架构。

若设计文档与实际代码不一致，Agent 必须先报告差异并以调查结果制定最小修改方案，不能根据旧行号直接改动。

## 5. 当前架构声明

- AI 出题只能由“出题 Agent + 审题 Agent”两层组成；允许有限的生成、审题和修订循环，不增加第三层出题 Agent。
- TutorHarness 的辅导角色不得参与出题流水线。
- 外部 LLM Provider 调用属于允许的模型能力；默认不进行网页搜索、爬取或外部教材检索，除非任务明确授权。
- `prompts_2` 中的八层出题、PID、FeedbackAggregator 和 SummaryAgent 自进化不再是当前强制架构。

## 6. 执行与风险规则

- 多文件任务必须先列出计划和影响范围。
- 删除文件、数据、数据库、容器或高风险配置前必须完成引用与目标核验，并取得明确授权。
- 数据库操作前记录并核验 `host`、`database`、`environment`；迁移与恢复先在独立可丢弃数据库验证，并准备备份和回滚。
- 数据层、ORM、API DTO、前端类型、展示、网关与环境变量要做耦合检查。
- 面向用户的错误为清晰纯文本，不暴露异常堆栈、SQL、密钥或内部对象；对象错误应提取 `message`。
- 修改代码后执行对应测试、构建、容器状态、日志和回归检查；仅修改文档不无意义重建 Docker。
- UI 变化必须使用内部浏览器完成真实操作、控制台、响应式和截图验收。

## 7. Prompts 4 协议

- 开始前读取 `docs/prompts_4/README.md`、全局执行规则和实施顺序。
- 一次只执行一个任务文件。
- HTML 报告中的候选文件和行号必须在当前代码中重新核验。
- 当前任务未验收通过前不得进入下一任务。
- 每项任务独立提交，并在 README 清单中区分“提示词存在”和“功能已实施”。

## 8. 验收

完成后必须满足：

- 根目录存在 `AGENTS.md`，且 `prompts_4` 引用可解析。
- `agent.md` 只作为兼容入口，不再包含八层、PID、自进化或失效 `agents/` 路径。
- `docs/INDEX.md` 同时链接标准入口和兼容入口。
- `AGENTS.md` 不包含本机绝对项目路径。
- 两层出题、四角色辅导、错误脱敏、数据库目标核验、内部浏览器和 Git 规则明确存在。
- 所有相对 Markdown 链接可解析。
- Git 变更只涉及 `AGENTS.md`、`agent.md`、`docs/INDEX.md` 和本设计/实施计划文档。
- `git diff --check` 通过。
