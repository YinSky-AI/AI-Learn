# P0/P1 验收遗留项补全设计

## 目标

以 `docs/prompts_4/03-acceptance-report.md` 为调查线索，按当前代码、测试和运行结果补齐仍未满足的 P0/P1 验收条件，并以完整交付门禁作为最终依据。

## 范围与优先级

1. 先恢复 P0-07/P0-08 的全量交付门禁：修正迁移演练诊断和基线，补齐关键用户路径的端到端验证。
2. 再补齐 P1 的核心可靠性边界：生成任务状态机与恢复、练习/导师/学习旅程的统一状态和 DTO、复习调度的一致性。
3. 最后强化账户、预算、诊断和跨库契约的测试证据；只在已有设计明确的范围内实现。

## 架构原则

- 报告中的旧结论必须重新由当前代码和自动化验证确认；已经修复的项只更新验收证据，不重复重构。
- 生成任务使用独立持久化任务记录、明确状态迁移、幂等键和租约；保持现有“出题 Agent + 审题 Agent”两层约束。
- 前端仅通过明确 DTO 与状态机消费学习 API；SSE 使用可中止、跨数据块安全的解析器。
- `next_review_at` 是复习到期判断的唯一事实来源，统计和取题共用同一语义。
- 安全、预算、审计和可观测性均使用可测试的服务边界，避免在路由层复制规则。

## 非目标与闸门

- 不实施 P2-20 的保留、删除、匿名化或未成年人数据规则；这些仍需要业务、法务和隐私书面确认。
- 不删除现有数据库数据、不推送远端、不修改用户的无关未提交变更。
- 异机/异故障域备份只能实现可配置和可验证的技术能力；真实生产外部存储需要用户提供已授权目标。

## 验收

- `python scripts/verify.py full` 完整通过。
- 后端完整测试、前端测试、类型检查和生产构建通过。
- Docker Compose 核心服务健康，`/health`、`/live`、`/ready` 返回预期。
- UI 变更使用内部浏览器完成真实路径验证，并保存截图和控制台证据。
- 每一项修复保留相应测试与验收证据，且不把外部授权闸门伪装为已完成。
